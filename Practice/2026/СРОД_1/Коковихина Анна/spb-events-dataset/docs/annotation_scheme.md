# Схема разметки: SPB Events Dataset

Документ описывает правила разметки для извлечения сущностей, отношений и последующей сборки графа знаний. Цель исследования — проверить, можно ли из туристических описаний надёжно извлекать **место**, **дату** и **историческое событие** при **связях многие-ко-многим** между достопримечательностями и событиями.

---

## 1. Единица разметки

- **Текстовый фрагмент (`doc_id`)**: 1–3 абзаца связного текста (экскурсионный стиль, путеводитель, аудиогид в виде транскрипта и т.п.).
- Каждый фрагмент обязан иметь `**landmark_id`**: основной объект, к которому относится материал (даже если в тексте упоминаются другие объекты).
- **Аудио / изображения** не размечаются сущностями внутри файла на первом этапе; для них фиксируются идентификаторы в метаданных и ссылка на тот же `landmark_id` (и опционально `doc_id`, если медиа однозначно соответствует конкретному тексту).

---

## 2. Типы сущностей

### 2.1. `LANDMARK`

Физический туристический объект: здание, ансамбль, монумент, музей в границах одного комплекса.

- **Правило:** в тексте размечайте **все** явные упоминания достопримечательностей, в том числе **второстепенные** (для связей M:N и для `RELATED_TO`).
- **Нормализация:** каждому вхождению в CSV сущностей сопоставьте `**entity_id`** из `metadata/landmarks.csv` (или временный `NEW_*` с пояснением в `note`, если объекта ещё нет в справочнике).

### 2.2. `PLACE`

Географическая или административная единица **шире**, чем один landmark: район, город, остров, река, площадь как локация, страна.

- **Отличие от `LANDMARK`:** «Васильевский остров» — `PLACE`; «Ростральные колонны» — `LANDMARK`.
- Вложенность отражается отношением `**LOCATED_IN`** (см. §4).

### 2.3. `DATE`

Календарная привязка: год, дата, диапазон, десятилетие, если в тексте выражено явно или однозначно **восстанавливается** из контекста (например, «в годы блокады» → в `note` пояснить интерпретацию и по возможности расширить нормализованное значение в `date_iso`).

- **Поверхность (`surface`):** как в тексте.
- **Нормализация:** поле `date_iso` в TSV (формат ниже) — по возможности `YYYY`, `YYYY-MM-DD` или интервал `YYYY/YYYY`.

### 2.4. `EVENT`

Исторический или культурный **эпизод**, который можно назвать событием: битва, коронация, открытие, пожар, революционный штурм, создание музейной коллекции и т.д.

- Одно и то же `**event_id`** может связываться с **несколькими** landmarks и наоборот (**M:N**).
- Если событие в тексте **не именовано**, но описано однозначно, создайте краткий `**canonical_name_ru`** в справочнике `metadata/events.csv` и стабильный `event_id`.

---

## 3. Смещения символов и кодировка

- Тексты и TSV хранятся в **UTF-8**.
- `**start_char`**, `**end_char**`: индексы в **Юникод-код-поинтах** (логических символах), полуоткрытый интервал `[start_char, end_char)` относительно **нормализованного текста документа**.
- **Нормализация текста для подсчёта оффсетов (обязательна до разметки):**
  - Один перевод строки между абзацами; без «мягких» переносов и лишних пробелов на границах абзацев.
  - Строки нормализованных текстов регистрируйте в `metadata/docs.csv`: `doc_id`, `landmark_id`, `language`, `source`, `license`, `text_relpath` (= `raw/text/<doc_id>.txt`), `audio_ids`, `image_ids` (несколько — через точку с запятой без пробелов, например `img_x;img_y`).

Если оффсеты временно недоступны, допускается `**start_char=-1`, `end_char=-1`** с заполнением `surface` и пометкой в `note`.

---

## 4. Типы отношений

Домены и кодомены задают **локальную семантику** в рамках датасета (для конвертации в RDF/Turtle их можно отобразить на свою онтологию).


| Отношение     | Базовая интерпретация                                                                                  | Типичный head → tail                                           |
| ------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `LOCATED_IN`  | Объект (landmark или place) находится внутри более крупной локации                                     | `LANDMARK` или `PLACE` → `PLACE`                               |
| `HAS_DATE`    | Сущность привязана ко времени (событие, период существования, дата создания фрагмента фактов в тексте) | `LANDMARK`, `PLACE`, `EVENT` → `DATE`                          |
| `RELATED_TO`  | Общая связь «упомянуто / ассоциировано» без более точного типа или как **дополнение** к фону           | любая пара сущностей из списка, если текст не позволяет точнее |
| `HAPPENED_AT` | Событие (частично) происходило у landmark                                                              | `EVENT` → `LANDMARK`                                           |
| `HAPPENED_ON` | Событие привязано к местности уровня `PLACE`                                                           | `EVENT` → `PLACE`                                              |


**Многие-ко-многим:**

- Одно `**EVENT`** может иметь несколько `**HAPPENED_AT**` / `**HAPPENED_ON**` к разным сущностям.
- `**RELATED_TO**` используйте скупо; предпочитайте более информативные отношения, когда контекст ясен.

## 5. Файл `annotations/text/entities.tsv`

Колонки (табуляция):


| Колонка       | Описание                                                                               |
| ------------- | -------------------------------------------------------------------------------------- |
| `doc_id`      | Уникальный ID текстового фрагмента                                                     |
| `landmark_id` | Основной объект материала (из `landmarks.csv`)                                         |
| `mention_id`  | Уникальный ID внутри `doc_id` (например `m01`, `m02`)                                  |
| `start_char`  | Начало вхождения в нормализованном тексте                                              |
| `end_char`    | Конец (не включительно)                                                                |
| `surface`     | Дословный фрагмент из текста                                                           |
| `entity_type` | `LANDMARK` | `PLACE` | `DATE` | `EVENT`                                                |
| `entity_id`   | ID из соответствующего справочника (`landmark_id`, `place_id`, `event_id`) или `NEW_*` |
| `date_iso`    | Для `DATE`: нормализация; иначе пусто                                                  |
| `note`        | Уточнения, неоднозначность, ссылка на источник                                         |


---

## 6. Файл `annotations/text/relations.tsv`


| Колонка           | Описание                                                         |
| ----------------- | ---------------------------------------------------------------- |
| `doc_id`          | ID фрагмента                                                     |
| `landmark_id`     | Тот же, что в строках сущностей этого фрагмента                  |
| `rel_id`          | Уникальный ID внутри `doc_id`                                    |
| `head_mention_id` | Ссылка на `mention_id` головы (из `entities.tsv`)                |
| `tail_mention_id` | Ссылка на `mention_id` хвоста                                    |
| `relation_type`   | Один из пяти типов                                               |
| `confidence`      | Опционально: `high` | `medium` | `low` (для обучения/фильтрации) |
| `note`            | Цитата-обоснование или комментарий                               |


**Согласованность:** `head_mention_id` и `tail_mention_id` должны существовать в `entities.tsv` для того же `doc_id`.

---

## 7. Экспорт в граф (опционально)

- Экспорт в RDF/TTL для human-only версии **не обязателен**.
- Если нужен граф, стройте триплеты из **нормализованных** `entity_id` (не из поверхностных форм).
- Для вхождений с `NEW_*` сначала добавьте запись в справочники и замените идентификатор.

---

## 8. Контроль качества (чек-лист)

1. У каждого `doc_id` есть хотя бы одна сущность типа `LANDMARK` или явное упоминание, маппящееся на `landmark_id`.
2. События, названные в тексте, размечены как `EVENT` и связаны датой через `HAS_DATE` или с локацией через `HAPPENED_AT` / `HAPPENED_ON`, если это выводимо.
3. Нет дублирующих `mention_id` в одном `doc_id`.
4. Оффсеты проверены вручную или любым удобным способом: `text[start_char:end_char] == surface`.
5. Связи M:N отражены **отдельными** строками в `relations.tsv`, а не объединением в одну запись.

---

## 9. Двойная разметка (опционально)

Если команда работает с двумя разметчиками, заведите два независимых слоя таблиц (`entities.tsv`/`relations.tsv`) вне основного контура и затем соберите арбитражный `gold`.

## 10. Мини-пример строк TSV

Пример вручную заполненных строк:

`entities.tsv`

```
doc_id	landmark_id	mention_id	start_char	end_char	surface	entity_type	entity_id	date_iso	note
doc_example_001	land_aurora	m01	0	16	Крейсер «Аврора»	LANDMARK	land_aurora		
doc_example_001	land_aurora	m02	35	39	1917	DATE		1917	
doc_example_001	land_aurora	m03	126	147	Октябрьской революции	EVENT	evt_aurora_blank_1917		
```

`relations.tsv`

```
doc_id	landmark_id	rel_id	head_mention_id	tail_mention_id	relation_type	confidence	note
doc_example_001	land_aurora	r01	m03	m01	HAPPENED_AT	high	
doc_example_001	land_aurora	r02	m03	m02	HAS_DATE	high	
```
